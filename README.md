# Довготривала пам'ять агента

Шаблон файлової довготривалої пам'яті для AI-агентів за методом Андрія Карпаті.
Працює з **Claude Code**, **Gemini CLI** та **AMP Code** на macOS, Linux і Windows.

Пам'ять це каталог markdown-файлів, який агент читає на початку сесії й дописує
після роботи. Не база даних і не плагін: звичайні файли, які читає й людина.

## Навіщо це потрібно

Агент без пам'яті щоразу починає з нуля. Ви пояснюєте одне й те саме, він знову
пропонує підхід, який ви вже відкинули місяць тому.

Пам'ять вирішує це так: рішення, причини помилок і напрацьовані підходи
зберігаються у файлах зі зв'язками між ними. Наступна сесія починається
з читання цих файлів.

## Швидкий старт

```bash
git clone https://github.com/ivanlysenk0/long-term-memory-vault-kit.git
cd long-term-memory-vault-kit
./install.sh
```

Windows, PowerShell:

```powershell
git clone https://github.com/ivanlysenk0/long-term-memory-vault-kit.git
cd long-term-memory-vault-kit
powershell -ExecutionPolicy Bypass -File .\install.ps1
```

Установник сам знайде встановлених агентів. Далі перезапустіть агента й скажіть:

> розгорни довготривалу пам'ять

Агент прочитає скіл і проведе вас через розвідку, установку та підключення.

## Що всередині

```
skill/
├── SKILL.md              інструкція для агента
└── scripts/
    ├── ltm_detect.py     розвідка машини перед установкою
    ├── ltm_init.py       установка, прийняття наявної пам'яті, підключення
    ├── ltm_doctor.py     перевірка здоров'я сховища
    ├── ltm_schedule.py   регулярна перевірка за розкладом
    ├── ltm_seed.py       передача готового вмісту пам'яті іншій людині
    └── ltm_uninstall.py  повне видалення пам'яті й слідів установки
install.sh                установка: macOS, Ubuntu, Debian, Fedora, Arch
install.ps1               установка: Windows
```

Залежностей немає. Потрібен лише **Python 3.8 або новіший**.

## Три шари пам'яті

| Шар | Де | Хто пише |
|-----|-----|---------|
| **Raw** | `<проєкт>/Raw/` | тільки людина. Агент читає й ніколи не змінює |
| **Wiki** | `knowledge/`, `atlas/`, `00-home/` | агент |
| **Schema** | файли правил і `operations.md` | людина |

Розділення принципове. Якщо агент пише в Raw, первинні джерела перестають бути
джерелами. Якщо людина руками править Wiki, агент втрачає зв'язність графа.

## Три операції

- **Ingest**: сирий матеріал перетворюється на сторінку знань зі зв'язками
- **Query**: відповідь на питання з посиланням на конкретні файли
- **Lint**: перевірка цілісності структури

## Ручне використання

Скрипти працюють і без агента.

```bash
# що вже є на машині
python3 skill/scripts/ltm_detect.py

# порівняти наявну структуру з каноном
python3 skill/scripts/ltm_detect.py --compare ~/memory

# нова пам'ять
python3 skill/scripts/ltm_init.py

# прийняти наявну структуру, нічого не ламаючи
python3 skill/scripts/ltm_init.py --adopt --path ~/memory

# підключити пам'ять до робочого проєкту
python3 skill/scripts/ltm_init.py --link ~/projects/my-app --providers claude,gemini

# перевірка здоров'я
python3 skill/scripts/ltm_doctor.py --vault ~/memory

# зібрати вміст пам'яті у зашифрований файл для колеги
python3 skill/scripts/ltm_seed.py --pack team.ltmseed --projects infra,qa

# влити такий файл у свою пам'ять
python3 skill/scripts/ltm_seed.py --unpack team.ltmseed --dry-run
```

## Перевірка здоров'я

`ltm_doctor.py` робить десять перевірок приблизно за секунду на 500 файлах:

- відсутній або неповний YAML-заголовок
- некоректний формат дати
- биті вікі-посилання, включно з тими, що **виглядають робочими**
- неправильний регістр в імені проєкту: `[[my-proj/log]]` при каталозі `My_Proj`
- відносні шляхи `../`, які Obsidian не розуміє
- дублікати імен сторінок
- сторінки без жодного вхідного посилання
- заготовки без змісту
- сесії, з яких ще не витягнуто знання
- скрипти в пам'яті, що відстали від версії скіла

Поставте в розклад однією командою:

```bash
python3 skill/scripts/ltm_schedule.py
```

За замовчуванням: **будні, 12:00**, вихідні пропускаються. Скрипт визначає систему
сам і питає підтвердження перед записом: Linux `cron`, macOS `launchd`,
Windows `schtasks`.

```bash
python3 skill/scripts/ltm_schedule.py --hour 9      # інший час
python3 skill/scripts/ltm_schedule.py --everyday    # і у вихідні
python3 skill/scripts/ltm_schedule.py --status      # що стоїть зараз
python3 skill/scripts/ltm_schedule.py --remove      # прибрати
```

## Передача пам'яті іншій людині

`ltm_seed.py` збирає вміст пам'яті в один зашифрований файл і зливає його
в пам'ять іншої людини. Це для випадку, коли новачок має почати не з порожньої
структури, а з уже накопиченим знанням команди.

```bash
# власник: зібрати
python3 skill/scripts/ltm_seed.py --pack team.ltmseed --projects infra,qa

# колега: подивитися, що буде, нічого не змінюючи
python3 skill/scripts/ltm_seed.py --unpack team.ltmseed --dry-run

# колега: влити
python3 skill/scripts/ltm_seed.py --unpack team.ltmseed
```

**Що відбирати.** Без `--projects` пакується вся пам'ять, разом з особистим.
Правило просте: перелічуй проєкти явно і лише ті, які стосуються роботи.
Проєкти про здоров'я, гроші, родину, переїзд у seed не потрапляють ніколи.
Перед відправкою переглянь список файлів, який друкує `--pack`.

**Чого скрипт не бере в архів** незалежно від вибору: `.git` (у ньому лежить
уся історія, включно з тим, що колись видаляли), `.obsidian`, кеші, логи,
маркер `.ltm-vault`.

**Нічого не перезаписується.** Якщо файл у колеги вже є і відрізняється,
seed-версія лягає поруч із суфіксом `.seed.md`, а рішення лишається за людиною.
Лікар пам'яті такі файли пропускає, тому вони не ламають перевірку.

**Шифрування:** ключ з пароля через scrypt, дані через AES-256-GCM.
GCM обраний свідомо: він ловить підміну файлу, а не лише ховає вміст.
Пароль передавай окремим каналом, не разом із файлом. Відкликати доступ
після передачі неможливо: файл уже в руках людини.

## Оновлення після виходу нової версії

Пам'ять і скрипти оновлюються окремо, це три різні кроки.

**Крок 1, скіл у каталозі агента.** Повторна установка і є оновлення:

```bash
cd long-term-memory-vault-kit
git pull
./install.sh          # Windows: powershell -ExecutionPolicy Bypass -File .\install.ps1
```

Після цього перезапустити агента, інакше він читає старий `SKILL.md` з пам'яті процесу.

**Крок 2, скрипти всередині самої пам'яті.** Установка їх навмисно не чіпає:
вона ідемпотентна і нічого не затирає, тому `<vault>/scripts/` лишається
на версії, з якої ви починали. Для оновлення є окремий режим:

```bash
python3 skill/scripts/ltm_init.py --update
python3 skill/scripts/ltm_init.py --update --path ~/memory/long-term-memory-vault
python3 skill/scripts/ltm_init.py --version    # яка версія стоїть зараз
```

`--update` перезаписує лише чотири виконувані файли в `<vault>/scripts/`:
лікаря, планувальник, seed і видалення. Структура, `knowledge/`, файли правил
і будь-який ваш текст не змінюються. Перед записом друкується перелік файлів
і питається підтвердження, після запису одразу запускається лікар.

Те саме є в меню без прапорців: пункт 2 при запуску `ltm_init.py`.

**Крок 3, структура і правила всередині пам'яті.** Це найважливіше і найменш
помітне. У корені пам'яті лежить файл правил (`CLAUDE.md`, `AGENTS.md`,
`GEMINI.md`), за яким агент працює з вашими записами: що читати першим, куди
зберігати, як називати файли. Установка його НЕ оновлює ніколи, тому агент
роками може працювати за правилами тієї версії, з якої ви починали.

```bash
python3 skill/scripts/ltm_init.py --migrate --dry-run   # спершу подивитися
python3 skill/scripts/ltm_init.py --migrate             # застосувати
```

Що робить міграція:

- **додає файли, яких у старих установках не було**: `00-global-home/00-home/index.md`,
  `operations.md`, `pending-concepts.md` у проєктах
- **оновлює файл правил, якщо ви його не редагували.** Як вона це знає: при
  установці в манифест записується відбиток згенерованого файлу. Відбиток
  збігся, значить ви файл не чіпали
- **не чіпає файл правил, якщо ви його змінювали.** Нова версія лягає поруч
  як `CLAUDE.md.new`, порівняти і перенести потрібне вирішуєте ви
- **ваші записи не чіпає взагалі**: `knowledge/`, `sessions/`, `Raw/` і будь-який
  ваш текст лишаються як є

Сухий прогін друкує повний перелік змін і нічого не пише. Робіть його завжди
першим.

**Сносити пам'ять і ставити заново не треба.** `ltm_uninstall.py` написаний для
тестування скіла на чистій машині, а не як крок оновлення: він видалить ваші
записи. Оновлення робиться на місці, трьома командами вище.

**Як зрозуміти, що пора.** Лікар сам порівнює версію в манифесті з власною
і пише попередження, якщо вони розійшлися:

```
Скрипти: у пам'яті 1.0.0, у скілі 1.1.0. Онови: ltm_init.py --update --path <vault>
```

Рядок друкується і в `--quiet`, бо за розкладом лікар ходить саме тихим режимом.
Версія зберігається в `.ltm-install-manifest.json`, поле `scripts_version`.
Якщо пам'ять ставили до появи версій, поле буде порожнє: це нормально,
перший же `--update` його проставить.

## Видалення: повернути машину у вихідний стан

Установник питає це першим ділом: встановити або видалити все, що він поставив.
Потрібно насамперед для перевірки на різних системах, бо без відкату скіл
тестується на машині рівно один раз.

```bash
python3 skill/scripts/ltm_uninstall.py --survey     # лише показати знайдене
python3 skill/scripts/ltm_uninstall.py --dry-run    # що буде видалено
python3 skill/scripts/ltm_uninstall.py              # видалити
python3 skill/scripts/ltm_uninstall.py --keep-vault # прибрати інтеграції, пам'ять лишити
```

Прибирається все: пам'ять, блоки в файлах правил робочих проєктів, запис
у планувальнику, скіл у каталогах агентів.

**Ваші власні файли не постраждають.** Якщо `CLAUDE.md` у проєкті існував
до установки, з нього вирізається лише блок пам'яті, а ваш текст лишається.
Що саме створив установник, записано в манифест усередині пам'яті.

Дія незворотна, тому потрібно надрукувати слово `ВИДАЛИТИ`. Копії пам'яті немає.

## Куди встановлюється скіл

| Агент | Каталог |
|-------|---------|
| Claude Code | `~/.claude/skills/ltm-vault/` |
| AMP Code | `~/.config/amp/skills/ltm-vault/` (Windows: `%APPDATA%\amp\skills\`) |
| Gemini CLI | `~/.gemini/skills/ltm-vault/` |

Опції установника: `--claude`, `--amp`, `--gemini`, `--all`, `--help`.

## Що варто знати одразу

- **Пам'ять локальна.** Синхронізації немає, копія одна. Резервне копіювання
  це відповідальність власника
- **Не ставте пам'ять усередину робочого репозиторію**: вона потрапить у коміт
- **Не тримайте дві пам'яті одночасно**: агент прочитає не ту
- **Відео й аудіо в пам'ять не кладуть.** Якщо сховище під git, бінарний файл
  залишиться в історії назавжди. Зберігайте текст розшифровки
- **WSL**: пам'ять на диску Windows (`/mnt/c`) працює в рази повільніше

## Мультипроєктність

Канон вимагає «одне сховище, один проєкт». Кілька проєктів в одному сховищі
можливі, але це свідоме відхилення з ціною: індекс читається на кожен запит,
тому кожен новий проєкт дорожчає для всіх інших.

Якщо обираєте мультипроєкт, тримайте індекс верхнього рівня чистим: тільки
навігація, жодних регламентів і списків «важливого».
