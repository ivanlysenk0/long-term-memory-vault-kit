# Довготривала пам'ять агента

Пам'ять це каталог markdown-файлів, який агент читає на початку сесії й дописує
після роботи. Не база даних, не плагін: звичайні файли, які читає людина.

## Три шари

| Шар | Де | Хто пише |
|-----|-----|---------|
| Raw | `<проєкт>/Raw/` | тільки людина, агент читає й ніколи не змінює |
| Wiki | `knowledge/`, `atlas/`, `00-home/` | агент |
| Schema | файли правил у корені та `operations.md` | людина |

Три операції: **Ingest** (сирий матеріал у сторінку знань), **Query** (відповідь
з посиланням на файли), **Lint** (перевірка цілісності).

## Інструменти

Усі в `scripts/`, потрібен лише Python 3.8+, без залежностей.

| Скрипт | Навіщо |
|--------|--------|
| `ltm_detect.py` | розвідка машини: ОС, редактор, наявна пам'ять, конфлікти |
| `ltm_init.py` | встановлення, прийняття наявної пам'яті, підключення до агентів |
| `ltm_doctor.py` | перевірка здоров'я: 10 перевірок, ~1 секунда на 500 файлів |
| `ltm_hooks.py` | хуки Claude Code: пам'ять піднімається й зберігається сама |
| `ltm_schedule.py` | ставить перевірку на розклад: cron, launchd або Планувальник Windows |
| `ltm_seed.py` | передає готовий вміст пам'яті іншій людині, зашифрованим файлом |
| `ltm_uninstall.py` | прибирає пам'ять і всі сліди установки, для повторного тестування |
| `ltm_version.py` | три версії одразу: скіл, пам'ять, GitHub. Крок 0 перед роботою |


## Хуки Claude Code

Без хуків пам'ять це просто папка: агент щосесії починає з нуля, а сказане
зникає під час стиснення контексту. Хуки роблять її робочою.

```
python3 scripts/ltm_hooks.py --status     що стоїть зараз
python3 scripts/ltm_hooks.py --dry-run    план без змін
python3 scripts/ltm_hooks.py --install    поставити
python3 scripts/ltm_hooks.py --uninstall  зняти лише наші хуки
```

| Подія | Що робить |
|-------|-----------|
| `SessionStart` | піднімає пам'ять у контекст; після стиснення повертає дамп |
| `PreCompact` | зберігає розмову до того, як контекст стиснуть |

| `Stop` | позначає кандидатів у knowledge, комітить і пушить пам'ять |

`Stop` ставиться лише тоді, коли сховище під git.

Що робить `Stop` по порядку: сканує свіжі session-логи на ознаки розбору
(архітектура, патерн, root cause, ухвалено рішення, порівняння) і при трьох
збігах дописує кандидата у `pending-concepts.md`, після чого комітить і
відправляє зміни. Сторінки не пише: їх складає агент, а рішення ухвалює людина.
На чистому дереві хук мовчки виходить, мережу не чіпає.

**Збереження сесії лишається за людиною.** Хуки піднімають пам'ять і страхують
сировину, але рішення про те, що гідне `knowledge/`, ухвалює людина командою
«збережи сесію». `SessionEnd` навмисно не ставимо: він спрацьовує лише при
явному завершенні, дублює `PreCompact` і суперечить канону Карпаті.

Чужі хуки на тих самих подіях не чіпаються, перед зміною робиться бекап
`settings.json`. Хуки читаються на старті сесії: після установки відкрий нову.

**Збереження сесії лишається за людиною.** `SessionEnd` спрацьовує лише при
явному завершенні (`/clear`, `/resume`, вихід із застосунку). Якщо людина
просто перестала писати й лишила вікно відкритим, подія не настане ніколи.
Тому основний шлях це прохання «збережи сесію», а хук лише страховка.

Хуки не вирішують, що гідне `knowledge/`, і не пишуть туди сторінки: скрипт
не розуміє змісту розмови. Він зберігає сировину й нагадує про неї.

## Порядок роботи

### 0. Перевірка версій, ДО будь-якої роботи з пам'яттю

Перше, що ти робиш, відкривши цей скіл. Не пропускай: скіл живе в трьох місцях
і вони розходяться непомітно.

```bash
python3 scripts/ltm_version.py --json
```

Скрипт сам знаходить пам'ять і повертає три версії: скіл на диску, скрипти
в пам'яті, свіжу версію з GitHub. Мережа необов'язкова: немає інтернету,
поле `remote` буде `null`, і це не блокер.

Що робити з відповіддю:

- `remote_drift: true`: у репозиторії новіша версія. **Зупинись і скажи людині**,
  не починай роботу мовчки. По суті: «Твоя пам'ять розгорнута версією X,
  у репозиторії вже Y. Поточна реалізація відрізняється від тієї, яку ставить
  нова версія. Оновити зараз?»
- `local_drift: true`: скрипти в пам'яті відстали від скіла. Те саме питання,
  але без мережі.
- обидва `false`: працюй далі, нічого не питай.

Після згоди людини оновлюєш сам, саме в цьому порядку:

```bash
cd <клон репо> && git pull && ./install.sh                    # 1. сам скіл
python3 scripts/ltm_init.py --update  --path <vault>          # 2. скрипти
python3 scripts/ltm_init.py --migrate --path <vault> --dry-run  # 3. показати
python3 scripts/ltm_init.py --migrate --path <vault>            # 4. застосувати
```

Крок 3 обов'язковий, його результат показуєш людині ДО кроку 4.

**Чесно скажи про обмеження.** Текст скіла вже у твоєму контексті, і після
`git pull` ти в цій же сесії пам'ятаєш стару редакцію. Перечитай `SKILL.md`
з диска. Якщо змінився сам порядок роботи, скажи прямо «перезапусти сесію»,
а не вдавай, що все підхопилося.

**Відмова це нормальна відповідь.** Людина може сказати «працюй як є».
Тоді працюєш за наявною версією і більше не повертаєшся до цього в цій сесії.

### 1. Розвідка, завжди перша

```bash
python3 scripts/ltm_detect.py
```

Покажи користувачеві зведення й **дочекайся рішення**. Нічого не встановлюй,
поки не зрозумів, що вже є на машині.

Детектор рахує вагу знайденої структури. **Вага 9 і вище означає, що пам'ять уже
є.** Не створюй другу: агент прочитає не ту й відповість неправильно.

### 2. Розбір знахідок

- **ОС і залежності**: Python 3.8+ обов'язковий, git опційний
- **Наявна пам'ять**: якщо знайдена, пропонуй `--adopt`, а не нову установку
- **Конфлікти**: пам'ять усередині робочого репозиторію потрапить у коміт

Порівнюй знайдену структуру **з каноном, а не з чиєюсь реалізацією**:

```bash
python3 scripts/ltm_detect.py --compare /шлях/до/пам'яті
```

Канон допускає різні імена папок. `sources/`, `Clippings/`, `inbox/` це те саме,
що `Raw/`. Відмінності від референсної розкладки це **не порушення**.

### 3. Установка

```bash
# нова пам'ять
python3 scripts/ltm_init.py

# прийняти наявну структуру, нічого не ламаючи
python3 scripts/ltm_init.py --adopt --path /шлях/до/пам'яті

# тільки діагностика, без змін
python3 scripts/ltm_init.py --check --path /шлях
```

### 4. Підключення до агентів

**Питай провайдера, не вгадуй.** У кожного свій файл правил:

| Агент | Файл у проєкті | Глобальний |
|-------|----------------|------------|
| Claude Code | `CLAUDE.md` | `~/.claude/CLAUDE.md` |
| AMP Code | `AGENTS.md` | `~/.config/amp/AGENTS.md` |
| Gemini CLI | `GEMINI.md` | `~/.gemini/GEMINI.md` |

```bash
python3 scripts/ltm_init.py --link /шлях/до/проєкту --providers claude,gemini
```

Блок вставляється між маркерами `<!-- ltm:start -->` і `<!-- ltm:end -->`,
наявний вміст файлу не затирається.

**Точка входу в пам'ять це `00-global-home/master-index.md`**, а не файл правил.
Файл правил відповідає на питання «як працювати», master-index на питання «що є».

### 5. Самоперевірка

Установник наприкінці робить 7 перевірок сам. Прочитай його вивід: якщо код
повернення 1, установка неповна, не кажи користувачеві «готово».

### 6. Здоров'я пам'яті

```bash
python3 scripts/ltm_doctor.py            # перевірка
python3 scripts/ltm_doctor.py --scout    # позначити сесії до компіляції
python3 scripts/ltm_doctor.py --all      # обидва кроки
```

ПОМИЛКА лагодиться одразу. УВАГА розбирається в процесі роботи.

### Розклад

Не лишай перевірку на волю користувача: порада «додай рядок у crontab» не
виконується ніколи. Постав розклад одразу, але **тільки за явною згодою**:
це зміна в системі, а не всередині пам'яті.

```bash
python3 scripts/ltm_schedule.py              # будні, 12:00, спитає підтвердження
python3 scripts/ltm_schedule.py --hour 9     # інший час
python3 scripts/ltm_schedule.py --everyday   # і у вихідні теж
python3 scripts/ltm_schedule.py --status     # що стоїть зараз
python3 scripts/ltm_schedule.py --remove     # прибрати
```

Механізм обирається за системою: Linux `cron`, macOS `launchd`, Windows `schtasks`.
На macOS саме `launchd`, бо cron там формально є, але Apple його не рекомендує
і під захистом приватності він мовчки не спрацьовує.

Установник пропонує розклад сам, після успішної самоперевірки. Прапорці
`--schedule` і `--no-schedule` керують цим без питань.

### 7. Наповнення пам'яті готовим вмістом

Порожня пам'ять для новачка марна: агент читає структуру й нічого в ній не знаходить.
`ltm_seed.py` вирішує це, передаючи вміст однією зашифрованою посилкою.

```bash
python3 scripts/ltm_seed.py --pack team.ltmseed --projects infra,qa   # у власника
python3 scripts/ltm_seed.py --unpack team.ltmseed --dry-run           # у колеги, показ
python3 scripts/ltm_seed.py --unpack team.ltmseed                     # у колеги, злиття
```

**Відбір робить людина, не ти.** Без `--projects` пакується вся пам'ять разом
з особистим. Ніколи не збирай seed без явного переліку проєктів і без показу
цього переліку власнику. Проєкти про здоров'я, гроші, родину, документи
в seed не потрапляють.

**Спочатку завжди `--dry-run`.** Він друкує, що додасться і де виникне конфлікт,
і нічого не пише.

**Злиття не перезаписує.** Наявний файл лишається, seed-версія лягає поруч
із суфіксом `.seed.md`. Далі це вирішує людина, а не агент. Лікар такі файли
пропускає, тому перевірка не ламається.

**Пароль окремим каналом.** І скажи прямо: після передачі відкликати доступ
неможливо, файл уже в чужих руках. Це не обмеження реалізації, це властивість
будь-якої передачі файлу.

Установник пропонує seed сам після успішної самоперевірки. Прапорці
`--seed` і `--no-seed` керують цим без питань.

### 9. Видалення: повернути машину у вихідний стан

Установник питає це першим ділом, ще до розвідки:

```
Що робимо?
  1. Встановити або оновити пам'ять
  2. Видалити все, що поставив цей скіл
```

Друга гілка потрібна насамперед для перевірки скіла на різних системах.
Без відкату скіл тестується на машині рівно один раз, а друга спроба вже
йде поверх залишків першої, і незрозуміло, що саме ти перевіряєш.

```bash
python3 scripts/ltm_uninstall.py --survey     # лише показати знайдене
python3 scripts/ltm_uninstall.py --dry-run    # що буде видалено
python3 scripts/ltm_uninstall.py              # видалити, зі словом-підтвердженням
python3 scripts/ltm_uninstall.py --deep       # якщо пам'ять лежить не там, де звично
python3 scripts/ltm_uninstall.py --keep-vault # прибрати інтеграції, пам'ять лишити
```

Прибирається п'ять видів слідів: сама пам'ять, блоки `<!-- ltm:start -->`
у файлах правил проєктів, файли правил, створені установником, запис
у планувальнику, скіл у каталогах агентів.

**Чуже не чіпається.** Якщо `CLAUDE.md` у проєкті існував до установки,
з нього вирізається тільки наш блок, а файл лишається з власним текстом.
Розрізняє це манифест `.ltm-install-manifest.json` усередині пам'яті:
установник пише туди, що саме створив, а що лише доповнив.

Якщо манифесту немає, скрипт шукає за маркером блока і прямо каже, що діє
за ознаками. Файли правил він при цьому не видаляє: без манифесту довести,
що файл наш, неможливо.

**Підтвердження словом, а не літерою.** Видалення пам'яті надто дороге,
щоб спрацювати від випадкового натискання, тому потрібно надрукувати
`ВИДАЛИТИ`. Для автотестів є `--yes`.

Після роботи скрипт сам перевіряє себе повторним пошуком: якщо щось лишилося,
код повернення 1 і порада запустити з `--deep`.

## Оновлення в користувача, у якого скіл уже стоїть

Два шари оновлюються різними командами, не плутай їх.

**Шар 1, скіл у каталозі агента.** `git pull` у клоні репозиторію, потім
`./install.sh`. Установник робить `cp -R`, тобто перезаписує, окремої команди
оновлення не треба. Після цього обов'язково перезапустити агента.

**Шар 2, скрипти всередині пам'яті.** Установка їх НЕ оновлює навмисно:
вона ідемпотентна, `write_once` і `install_doctor` пропускають наявний файл.
Для цього окремий режим:

```
python3 ltm_init.py --update                       шлях за замовчуванням
python3 ltm_init.py --update --path <vault>        явний шлях
python3 ltm_init.py --update --path <vault> --yes  без підтвердження
python3 ltm_init.py --version --path <vault>       порівняти версії
```

Перезаписуються рівно чотири файли в `<vault>/scripts/`: `ltm_doctor.py`,
`ltm_schedule.py`, `ltm_seed.py`, `ltm_uninstall.py`. Нічого іншого режим
не чіпає: ані структури, ані `knowledge/`, ані файлів правил, ані тексту.
Перед записом друкується перелік і питається підтвердження, після запису
одразу викликається лікар.

**Версія живе в манифесті**, поле `scripts_version` у `.ltm-install-manifest.json`.
Лікар порівнює її зі своєю і пише УВАГА при розходженні, рядок видно і в `--quiet`.
У пам'яті, поставленій до появи версій, поля немає: це не помилка, перший
`--update` його проставить.

**Типова ситуація в користувача зі старою установкою:** `ltm_uninstall.py`
в `<vault>/scripts/` взагалі немає, бо його додали пізніше, а лікар лежить
версії місячної давнини. Обидва випадки закриває один `--update`.

**Шар 3, структура і правила всередині пам'яті.** Найважливіше і найменш
помітне. Файл правил у корені пам'яті визначає, ЯК агент працює із записами,
і установка його не оновлює ніколи.

```
python3 ltm_init.py --migrate --path <vault> --dry-run   завжди спершу
python3 ltm_init.py --migrate --path <vault>             застосувати
```

- додає файли, яких у старих установках не було
- оновлює файл правил, лише якщо людина його не редагувала: перевіряється
  відбитком `rules_hash` у манифесті, а не здогадом
- у пам'яті, поставленій до появи відбитків, судити нема за чим. Тоді скрипт
  каже «правила старішої версії, чи ви їх правили, невідомо» і не чіпає жодного
  файлу: кладе `.new` поруч і пропонує `diff`. Ніколи не пиши людині
  «ви змінювали руками», якщо відбитка немає: це буде неправда
- редагований файл не чіпає, кладе нову версію поруч як `.new`
- `knowledge/`, `sessions/`, `Raw/` не чіпає взагалі

**Ніколи не пропонуй «знести пам'ять і поставити заново».** `ltm_uninstall.py`
для тестування на чистій машині, а не для оновлення: він видалить записи людини.
Оновлення завжди на місці.

## Що скіл пише в робочі проєкти

Головний текст усього скіла. Агент відкривається в робочому проєкті, а не
всередині сховища, тому файл правил у корені пам'яті він не побачить ніколи.
Усе потрібне має бути в блоці, який лягає у `CLAUDE.md` / `AGENTS.md` /
`GEMINI.md` самого проєкту.

Склад блоку відповідає канону Карпати: три шари і три операції.

| Що | Навіщо |
|----|--------|
| шар Raw | `<проєкт>/Raw/` пише лише людина, агент читає й ніколи не змінює |
| шар Wiki | `knowledge/`, `00-home/` веде агент |
| шар Schema | сам блок і `00-home/operations.md` |
| операція Query | відповідь починається з `index.md` проєкту, а не з здогаду |
| операція Ingest | сировина з `Raw/` -> тези -> **пауза й підтвердження** -> сторінки |
| операція Lint | сироти, биті посилання, заглушки, застарілі твердження |
| Query -> Save | що саме зобов'язані зберегти, а що ні |
| `index.md` | оновлюється **в момент** створення сторінки, а не наприкінці сесії |
| вікі-посилання | шлях від кореня сховища, `../` заборонені |

**Мова блоку визначається автоматично** по наявному файлу правил проєкту:
українська, російська або англійська. Людина вже відповіла на це питання,
коли писала свій `CLAUDE.md`, питати вдруге зайве.

**Ім'я каталогу в сховищі зіставляється, а не вгадується.** На диску проєкт
може називатися `Sky-Kids-SMM-bot`, а в пам'яті `sky-kids-smm-bot`. Канон
однакових імен не вимагає, тому скіл шукає збіг без урахування регістру
й роздільників, а якщо однозначного збігу немає, питає людину.

## Точка входу: один проєкт чи кілька

| Проєктів | Точка входу | Чому |
|----------|-------------|------|
| один | `index.md` у корені | канон Карпати, `00-global-home` не створюється |
| кілька | `00-global-home/master-index.md` | потрібен рівень над індексами проєктів |

Назвати мастер-індекс теж `index.md` не можна: у проєктів є свої `index.md`,
і два різні файли з однією назвою плутають і агента, і людину.

Наявна точка входу завжди сильніша за розрахунок: перейменування зламало б
усі посилання на неї.

## Межі: чого скіл не робить ніколи

- **`--yes` не підключає проєкти.** Він означає «не став питань про мою
  пам'ять», а не «правь файли, яких я тобі не називав». Редагування чужих
  файлів завжди вимагає явного `--link`
- **Пам'ять у тимчасовій теці в робочі проєкти не пишеться.** Шлях із `/tmp`
  після перезавантаження зникне, а інструкція «пам'ять лежить тут» залишиться
- **Після установки перевіряються самі записані шляхи.** Блок може лягти
  успішно, але вказувати в нікуди; тоді самоперевірка дає ЗБІЙ, а не «готово»

## Мультипроєктність

Канон вимагає «одне сховище, один проєкт». Кілька проєктів в одному сховищі це
**свідоме відхилення**, і воно має ціну: індекс читається на кожен запит, тому
кожен новий проєкт дорожчає для всіх інших.

Якщо користувач обирає мультипроєкт, зафіксуй ціну в `operations.md` і тримай
індекс верхнього рівня чистим: тільки навігація, жодних регламентів.

## Підводні камені

- **Пам'ять усередині робочого репозиторію** потрапить у коміт. Ставити в домашній
  каталог, поза репозиторіями й поза хмарними теками синхронізації
- **Дві пам'яті одночасно**: агент прочитає не ту. Або adopt, або явне рішення власника
- **WSL і `/mnt/c`**: пам'ять на диску Windows із WSL працює в рази повільніше
- **Windows і кирилиця**: перед запуском `chcp 65001`
- **Bash-версії цих скриптів не портуй.** Оригінал викликав `find` усередині циклу:
  на 500 файлах це 3,5 хвилини проти 0,9 секунди в Python
- **Екранування `\|` у вікі-посиланнях** обов'язкове всередині таблиць Obsidian
- **Файли правил не є концепт-сторінками**, доктор їх виключає
- **Резервна копія**: пам'ять локальна, копія одна. Скажи про це власникові

## Помилки, знайдені на бойовій пам'яті

Усе нижче виявлено на сховищі з 500 файлів і 15 проєктів.

- **Посилання зі шляхом, перевірене за коротким іменем, брехало.** Доктор шукав `log`
  по всьому сховищу, знаходив чужий `log.md` і вважав `[[my-proj/log]]` живим. Каталог
  називався `My_Proj`, посилання вело в нікуди. Так мовчки зламалися 24 посилання
  одного проєкту. Тепер посилання зі `/` перевіряється буквально
- **Відносні шляхи `../` Obsidian не розуміє.** Виглядають розумно, не працюють
- **Правила поза пам'яттю не їдуть разом із нею.** Якщо загальні правила лежать
  у файлі налаштування машини, при копіюванні пам'яті колега отримає структуру
  без регламенту. Тому `operations.md` створюється всередині пам'яті
- **Індекс верхнього рівня розростається**, якщо в глобального проєкту немає власного.
  Знання загального рівня починають перелічуватися прямо в master-index
- **Регламент трекера задач це не навігація.** Правила роботи з задачами належать
  до `operations.md`, в індексі лишається рядок із посиланням
- **Блоки живуть довше за свою причину.** Список прямих посилань на службові файлы
  кожного проєкту має сенс при одному проєкті й стає дублем при десяти
- **Перед видаленням будь-якого блоку посилань перевір кожне скриптом**, не очима

## Коротко

1. `ltm_detect.py`, показати зведення, дочекатися рішення
2. розібрати конфлікти й залежності
3. `ltm_init.py` у потрібному режимі
4. `--link` на робочі проєкти
5. прочитати блок самоперевірки
6. перевірити вживу: спитати агента про порядок читання пам'яті
7. запропонувати розклад для доктора й нагадати про резервну копію
