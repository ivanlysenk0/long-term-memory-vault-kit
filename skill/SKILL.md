# Довготривала пам'ять агента

Пам'ять це каталог markdown-файлів, який агент читає на початку сесії й дописує
після роботи. Не база даних, не плагін: звичайні файли, які читає людина.

## Три шари

| Шар | Де | Хто пише |
|-----|-----|---------|
| Raw | `<проєкт>/Raw/` | тільки людина, агент читає й ніколи не змінює |
| Wiki | `knowledge/`, `atlas/`, `00-home/` | агент |
| Schema | файли правил у корені та `operations.md` | людина |

Три операції: **Ingest** (сирий матеріал у сторінку знань), **Query** (відповідь
з посиланням на файли), **Lint** (перевірка цілісності).

## Інструменти

Усі в `scripts/`, потрібен лише Python 3.8+, без залежностей.

| Скрипт | Навіщо |
|--------|--------|
| `ltm_detect.py` | розвідка машини: ОС, редактор, наявна пам'ять, конфлікти |
| `ltm_init.py` | встановлення, прийняття наявної пам'яті, підключення до агентів |
| `ltm_doctor.py` | перевірка здоров'я: 9 перевірок, ~1 секунда на 500 файлів |

## Порядок роботи

### 1. Розвідка, завжди перша

```bash
python3 scripts/ltm_detect.py
```

Покажи користувачеві зведення й **дочекайся рішення**. Нічого не встановлюй,
поки не зрозумів, що вже є на машині.

Детектор рахує вагу знайденої структури. **Вага 9 і вище означає, що пам'ять уже
є.** Не створюй другу: агент прочитає не ту й відповість неправильно.

### 2. Розбір знахідок

- **ОС і залежності**: Python 3.8+ обов'язковий, git опційний
- **Наявна пам'ять**: якщо знайдена, пропонуй `--adopt`, а не нову установку
- **Конфлікти**: пам'ять усередині робочого репозиторію потрапить у коміт

Порівнюй знайдену структуру **з каноном, а не з чиєюсь реалізацією**:

```bash
python3 scripts/ltm_detect.py --compare /шлях/до/пам'яті
```

Канон допускає різні імена папок. `sources/`, `Clippings/`, `inbox/` це те саме,
що `Raw/`. Відмінності від референсної розкладки це **не порушення**.

### 3. Установка

```bash
# нова пам'ять
python3 scripts/ltm_init.py

# прийняти наявну структуру, нічого не ламаючи
python3 scripts/ltm_init.py --adopt --path /шлях/до/пам'яті

# тільки діагностика, без змін
python3 scripts/ltm_init.py --check --path /шлях
```

### 4. Підключення до агентів

**Питай провайдера, не вгадуй.** У кожного свій файл правил:

| Агент | Файл у проєкті | Глобальний |
|-------|----------------|------------|
| Claude Code | `CLAUDE.md` | `~/.claude/CLAUDE.md` |
| AMP Code | `AGENTS.md` | `~/.config/amp/AGENTS.md` |
| Gemini CLI | `GEMINI.md` | `~/.gemini/GEMINI.md` |

```bash
python3 scripts/ltm_init.py --link /шлях/до/проєкту --providers claude,gemini
```

Блок вставляється між маркерами `<!-- ltm:start -->` і `<!-- ltm:end -->`,
наявний вміст файлу не затирається.

**Точка входу в пам'ять це `00-global-home/master-index.md`**, а не файл правил.
Файл правил відповідає на питання «як працювати», master-index на питання «що є».

### 5. Самоперевірка

Установник наприкінці робить 7 перевірок сам. Прочитай його вивід: якщо код
повернення 1, установка неповна, не кажи користувачеві «готово».

### 6. Здоров'я пам'яті

```bash
python3 scripts/ltm_doctor.py            # перевірка
python3 scripts/ltm_doctor.py --scout    # позначити сесії до компіляції
python3 scripts/ltm_doctor.py --all      # обидва кроки
```

ПОМИЛКА лагодиться одразу. УВАГА розбирається в процесі роботи.

Постав у розклад:
```
0 20 * * * python3 "<пам'ять>/scripts/ltm_doctor.py" --all --quiet
```

## Мультипроєктність

Канон вимагає «одне сховище, один проєкт». Кілька проєктів в одному сховищі це
**свідоме відхилення**, і воно має ціну: індекс читається на кожен запит, тому
кожен новий проєкт дорожчає для всіх інших.

Якщо користувач обирає мультипроєкт, зафіксуй ціну в `operations.md` і тримай
індекс верхнього рівня чистим: тільки навігація, жодних регламентів.

## Підводні камені

- **Пам'ять усередині робочого репозиторію** потрапить у коміт. Ставити в домашній
  каталог, поза репозиторіями й поза хмарними теками синхронізації
- **Дві пам'яті одночасно**: агент прочитає не ту. Або adopt, або явне рішення власника
- **WSL і `/mnt/c`**: пам'ять на диску Windows із WSL працює в рази повільніше
- **Windows і кирилиця**: перед запуском `chcp 65001`
- **Bash-версії цих скриптів не портуй.** Оригінал викликав `find` усередині циклу:
  на 500 файлах це 3,5 хвилини проти 0,9 секунди в Python
- **Екранування `\|` у вікі-посиланнях** обов'язкове всередині таблиць Obsidian
- **Файли правил не є концепт-сторінками**, доктор їх виключає
- **Резервна копія**: пам'ять локальна, копія одна. Скажи про це власникові

## Помилки, знайдені на бойовій пам'яті

Усе нижче виявлено на сховищі з 500 файлів і 15 проєктів.

- **Посилання зі шляхом, перевірене за коротким іменем, брехало.** Доктор шукав `log`
  по всьому сховищу, знаходив чужий `log.md` і вважав `[[my-proj/log]]` живим. Каталог
  називався `My_Proj`, посилання вело в нікуди. Так мовчки зламалися 24 посилання
  одного проєкту. Тепер посилання зі `/` перевіряється буквально
- **Відносні шляхи `../` Obsidian не розуміє.** Виглядають розумно, не працюють
- **Правила поза пам'яттю не їдуть разом із нею.** Якщо загальні правила лежать
  у файлі налаштування машини, при копіюванні пам'яті колега отримає структуру
  без регламенту. Тому `operations.md` створюється всередині пам'яті
- **Індекс верхнього рівня розростається**, якщо в глобального проєкту немає власного.
  Знання загального рівня починають перелічуватися прямо в master-index
- **Регламент трекера задач це не навігація.** Правила роботи з задачами належать
  до `operations.md`, в індексі лишається рядок із посиланням
- **Блоки живуть довше за свою причину.** Список прямих посилань на службові файлы
  кожного проєкту має сенс при одному проєкті й стає дублем при десяти
- **Перед видаленням будь-якого блоку посилань перевір кожне скриптом**, не очима

## Коротко

1. `ltm_detect.py`, показати зведення, дочекатися рішення
2. розібрати конфлікти й залежності
3. `ltm_init.py` у потрібному режимі
4. `--link` на робочі проєкти
5. прочитати блок самоперевірки
6. перевірити вживу: спитати агента про порядок читання пам'яті
7. запропонувати розклад для доктора й нагадати про резервну копію
